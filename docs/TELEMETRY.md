# Телеметрия и развитие знаний

Техническая статистика и структурированные маршруты включены по умолчанию в установленной и portable-версиях. Экранов согласия при запуске и обновлении нет. Переключатели находятся в **Настройки → Настройки приложения → Данные и конфиденциальность** и работают во время задачи. Главный выключатель останавливает оба вида передачи. Отключение маршрутов оставляет счётчики использования.

Разработка не отправляет события. `ARCHI_TELEMETRY_DISABLED=1` запрещает передачу и в упакованном приложении; интерфейс не может отменить это ограничение. Проверочные события используют `environment=test`, рабочие — `production`. Панели исключают проверочные события.

## Что передаётся

Случайный UUID профиля приложения, версия приложения, платформа и архитектура, тип установленной/portable-сборки; тип провайдера и способ подключения; публичное имя модели; Archicad/build/Tapir; длительности, токены, число задач, генераций, HTTP-попыток, инструментов и сжатий контекста; фиксированные категории ошибок и задач; ID встроенных статей. Имена моделей и команд проверяются по поставляемому разрешённому каталогу. Неизвестные модели обозначаются `custom`, команды — `other`.

Для маршрутов добавляются не более 60 шагов `{tool, command, status, error_category}`, признак усечения и полноты наблюдения. Произвольный Python представлен одним шагом: внутренние вызовы, ветвления и параметры не извлекаются. Не следует выдавать такой маршрут за полную программу решения. Фиксированная категория задачи определяется локально; исходный текст не передаётся.

При включённом развитии знаний события `archi_tool_diagnostic` содержат технический отчёт по шагу: распознанную причину ошибки, составленное по шаблону пояснение, разрешённые имена полей API и структуру входа/ответа с типами вместо значений. Например, можно отличить неверное поле аргумента, отсутствующий ключ словаря, неверный тип значения и ошибку внутри `executionResults`. Неподдерживаемые тексты заменяются общей причиной; это не сбор произвольных сообщений исключений. Словарь полей в `electron/telemetry-diagnostic-fields.json` получен только из поставляемых публичных схем Tapir.

`step_index` связывает отчёт с маршрутом. `previous_failed_step` указывает предыдущую неудачу того же инструмента и публичной команды; это не доказательство причинной связи или правильности исправления. Структуры ограничены глубиной, числом полей и узлов; массив представлен формой одной записи без исходных значений и количества элементов. Поля отчёта повторно проверяются перед отправкой, текст восстанавливается из разрешённых шаблонов. Выключение развития знаний удаляет из очереди и маршруты, и технические отчёты.

Не передаются тексты чата, рассуждения или ответы моделей, файлы, PDF, изображения, названия проектов и аккаунтов, адреса пользовательских серверов, пути, GUID элементов, ключи, OAuth-данные, значения аргументов инструментов, скрипты, исходный вывод команд, сообщения исключений и stack trace. Личные статьи базы знаний исключены. Хеширование этих данных не используется как способ их публикации.

Схема 3 расширяет технические отчёты: сохраняет разрешённые типы `AssertionError`, `ArchicadError` и `UnsucceededCommandCall`, а известные ошибки API переводит в фиксированные категории (`unsupported_element_class`, `invalid_program_status`, `parameter_change_failed`). Исходные сообщения и числовые значения из них не передаются. Ошибки в `elements` и `attributeIds` проверяются так же, как в `executionResults`.

При включённом развитии знаний `run_python` наблюдает JSON-запросы через `urllib.request.urlopen` к явно выбранному локальному порту Archicad. Этот путь используют поставляемые Tapir-клиент и Graphisoft SDK. Для каждого из первых 40 вызовов отправляется отдельный `archi_tool_diagnostic` с `source=python_json_api`, индексом родительского шага и `api_step_index`, публичным именем команды, формой полей и нормализованным результатом. Аргументы и ответы возвращаются скрипту без изменения; отдельные ошибки API видны даже при нулевом коде завершения Python. Счётчик инструментов учитывает только внешний вызов `run_python`.

Внешний отчёт указывает `api_coverage`, `api_observed`, `api_truncated`, `api_has_failures` и отдельно `api_outcome_unknown`. Это покрытие конкретного транспорта, а не всех действий Python: другие HTTP-библиотеки, дочерние процессы и неизвестные команды не дают полного маршрута. Размер наблюдаемого запроса/ответа ограничен 2 МиБ; чтение ответа частями, превышение лимита и повреждённый журнал помечаются как неполное наблюдение. Не прочитанный до конца результат остаётся неизвестным. Служебный журнал содержит только разрешённые метаданные, ограничен при чтении 512 КиБ и удаляется после процесса. При отключённых маршрутах наблюдатель не запускается; последующее выключение инвалидирует передачу текущей задачи по обычным правилам.

Проверка ответа API по-прежнему имеет `verification=unverified`: она не подтверждает геометрию, сравнение значений после чтения или цель пользователя. Последовательность запросов помогает выбрать независимую синтетическую проверку. Локальная запись запуска дополнительно сохраняет версии приложения и схемы для последующего сопоставления; старые записи не дополняются задним числом.

Идентификаторы задач для телеметрии создаются независимо от идентификаторов проектов и чатов. UUID профиля позволяет связывать события между запусками: статистика псевдонимная, не анонимная. Несколько профилей одного человека считаются отдельно. Первый наблюдаемый запуск не равен скачиванию или установке; `existing_profile` помечает существовавшие до интеграции профили с провайдерами/проектами. Выключенная телеметрия, офлайн, сбои и очистка профиля ограничивают точность.

## Доставка и отключение

Используется официальный HTTP API PostHog (`/batch/`), европейский endpoint и сетевой транспорт Electron с системным прокси. Схема полей проверяется до очереди и повторно перед отправкой. Автоматические сборщики SDK, запись сессий, консоли, кликов, исключений и геолокационное обогащение не используются. На стороне проекта включено удаление IP. Как и при любом HTTPS-запросе, принимающая инфраструктура видит сетевой адрес соединения.

Очередь только в памяти: до 1000 событий сроком до 24 часов, отправка до 50 событий каждые 15 секунд. Сбои не влияют на выполнение задач. Временные ошибки повторяются с увеличивающейся задержкой; постоянные ошибки не вызывают бесконечную отправку одного пакета. Закрытие приложения ждёт не более 1,5 секунды. Доставка не гарантирована, особенно при аварийном завершении.

Отключение немедленно очищает очередь, отменяет активный запрос и инвалидирует наблюдения текущей задачи. При повторном включении прежние задачи не выгружаются. Уже принятый сервером пакет отменить невозможно. При ошибке сохранения настройки передача блокируется до успешного повторного сохранения; интерфейс сообщает об ошибке.

Ранее отправленные данные хранятся согласно настройкам хранения проекта PostHog. Для удаления пользователь передаёт разработчику UUID из настроек приватным каналом. Разработчик удаляет события для этого `distinct_id` через административный API/MCP и проверяет завершение удаления. Запись UUID в локальном профиле сама по себе не является запросом удаления.

## Метрики результата

`archi_task_started/finished` считают запуск задачи; уточнения внутри неё учитываются в `steering_count`. `$ai_generation` считает логическую генерацию, включая сжатие контекста (`purpose=compaction`). `archi_http_request` считает физическую попытку запроса модели, включая повторы. OAuth-токен-запросы и содержимое HTTP не собираются.

Исходы: `completed_unverified`, `failed`, `cancelled`, `outcome_unknown`. Завершённый ответ модели и нулевой код возврата Python не являются доказательством решения. Для прерванных изменений сохраняется неизвестный исход. Неудачный промежуточный инструмент может сопровождаться последующим завершением задачи — счётчики ошибок сохраняются.

Ошибка отдельной записи `executionResults`, включая `success:false`, считается ошибкой шага даже при успешной доставке MCP. В техническом отчёте указано, проверялись ли такие результаты или только отсутствие признака ошибки инструмента. Проверка геометрии, бизнес-результата и действий внутри произвольного Python из этих признаков не выводится. Старые события схемы 1 не пересчитываются в события схемы 2 и могут не учитывать вложенные ошибки.

Токены берутся только из ответа провайдера; отсутствие usage не заменяется нулём. Денежная стоимость не рассчитывается приложением: тариф подписки или шлюза может отличаться от публичной цены модели. Рейтинг «Решена / Не решена / Не уверен» добровольный и не заменяет техническую проверку. Изменённая оценка создаёт новое событие; при анализе индивидуального результата используйте последнюю оценку по `run_id`.

## Из наблюдений в знания

1. В приватной панели опыта изучите частые ошибки, последовательности действий и оценки. Это недоверенные наблюдения: публичный токен приёма нельзя использовать для аутентификации отправителя.
2. Выделите техническую гипотезу и область применимости. Не переносите исходную сессию, её идентификаторы, время, количества элементов или результаты проекта в заметки и статьи.
3. Подготовьте самостоятельный синтетический пример и воспроизведите его в отдельном тестовом проекте. Не объявляйте успешным результат, который проверен только словами модели.
4. Оформите Markdown-статью в `electron/knowledge`: условия, точные схемы API, необходимые разрешения, порядок действий, проверка и восстановление. Добавьте `triggers` и `related` для раннего подбора.
5. Для узкой применимости используйте `compatibility`, например синтетическую границу `[{"archicad":99,"minBuild":1000,"maxBuild":2000,"tapirMin":"9.0.0","tapirMax":"9.1.0"}]`. Это пример формата, не утверждение поддержки. Неизвестный build/Tapir не проходит ограничение. `verifiedOn` по-прежнему описывает историческую проверку, а не новый запуск.
6. Проведите просмотр diff, штатные проверки и обычный выпуск. Сырые события не загружаются в контекст модели. Подбор использует только локальные проверенные статьи; их текст не предоставляет разрешений на действия.

Отдельный сервис для хранения исходных переписок не требуется: очередь технических наблюдений находится в PostHog. Автоматическая публикация новых инструкций не включена. Доставка проверенных знаний выполняется обычными релизами приложения.

## Настройка и сопровождение PostHog

Схемы событий определены в `electron/telemetry-schema.mjs`. Адреса приватных панелей, идентификаторы проекта и конфигурация приёма хранятся локально у сопровождающего, вне репозитория. В документации описываются только общие принципы и синтетические примеры.

Персональный административный ключ не нужен приложению. Не добавляйте его в исходники, историю Git, сборку или пользовательский профиль. Параметры конкретной установки аналитики передаются через локальную конфигурацию или закрытые настройки сборки.

Локальная сборка читает `ingestion.json` из каталога сопровождающего вне репозитория или файла, указанного через `ARCHI_TELEMETRY_CONFIG_FILE`. Переменные `ARCHI_POSTHOG_PROJECT_TOKEN` и `ARCHI_POSTHOG_HOST` переопределяют параметры; в bundle попадает только публичный токен приёма. Релиз с `ARCHI_REQUIRE_TELEMETRY_CONFIG=1` не собирается без токена. Сборка для разработки без конфигурации ничего не отправляет. Идентификаторы проекта и ссылки на панели не требуются работающему приложению.

Рабочие события имеют `environment=production`, проверочные — `test`. Фильтр исключения тестовых событий должен сохранять рабочие события. После изменения фильтров принудительно пересчитайте графики, чтобы не читать устаревший кеш.
