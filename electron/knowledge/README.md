# Markdown-база знаний

Промпты и системные статьи поставляются с приложением; личные записи хранятся отдельно в профиле. Канонический источник — Markdown, реестр в JavaScript больше не нужен.

`prompts/` хранит системные инструкции, `common/` — общие процедуры, `versions/25/` и `versions/27/` — отличия и границы проверки по версиям. Общий текст не дублируется. Для неизвестной версии доступны только общие статьи; отсутствие наблюдений не означает подтверждённой поддержки. Совпадение версии/build/Tapir с метаданными не означает нового успешного запуска.

Перед ответом локальный подбор подключает подходящие `auto`-статьи по тексту задачи. Для встроенных статей `triggers` задаёт ключевые слова, а `related` — ID связанных процедур; зависимости проходят тот же фильтр версии и режима. Например, PDF-задача подключает `layout-audit`, `archicad-capabilities` и заметку текущей версии. Подбор обновляется при уточнении задачи, подключения и используемых инструментов. До трёх основных совпадений, вместе с зависимостями — до шести статей и 12 000 символов; не поместившиеся статьи перечисляются как доступные для чтения по ID. Ручные статьи не подключаются даже через зависимости. В чате показаны названия автоматически подключённых статей.

`get_knowledge(query, offset, limit)` позволяет дополнительно искать метаданные; `get_knowledge(id)` — читать текст одной статьи. Поиск локальный по словам в названии, тегах, описании и тексте. В системное сообщение входят только количество доступных записей, ID уже подключённых статей и параметры подключения. Полный список названий и полная база автоматически не отправляются. Тексты кешируются по размеру и времени изменения, добавление и удаление файлов обнаруживаются при обращении.

Личные файлы находятся в `<профиль>/knowledge/global/` и `<профиль>/knowledge/projects/<projectId>/`, вне каталога установки и хранилища чатов. Обновления и удаление проекта их не удаляют. `.history/` хранит предыдущие редакции, `.trash/` — восстановимые удалённые записи; автоматической очистки нет. [Формат и лимиты](USER-GUIDE.md).

Режимы: `auto` — автоматический подбор и поиск; `manual` — чтение и поиск агентом запрещены до выбора пользователем; `always` — короткий пользовательский контекст каждого подходящего запроса. Выбранные вручную тексты сохраняются в запросе как снимок, включая очередь. Уже отправленная информация остаётся в истории. Знание — справка, навык — процедура; оба являются контекстом для модели, а не исполняемым плагином или разрешением на действия.

При добавлении приёма:

1. Создайте Markdown-файл с уникальным `id`, полями `title`, `summary`, `kind`, `activation`, `enabled`, `tags`, `archicad` в заголовке между `---`. Реестр формируется автоматически. В `versions/<N>/` обязательно `archicad: [N]`. Сложный YAML не поддерживается: одна строка на поле, JSON для массивов. Дополнительное `verifiedOn` — JSON-массив `{archicad, build, tapir}`.
2. Укажите задачу, область применимости, источник и дату проверки, необходимые разрешения, исходные данные, порядок действий, проверку и восстановление.
3. Разделяйте исторически проверенное поведение и предположения. Примеры GUID, значений и версий не являются данными текущего проекта. Не включайте пользовательские файлы, ключи или полные журналы проекта.
4. Перед вызовом сверяйте точную схему и доступность команды с каталогом текущего подключения. Статья не делает команду доступной на любой версии Archicad/Tapir.
5. Если приём требует отдельного согласия, явно укажите это в статье и системных инструкциях. Для такого приёма передавайте `knowledge_id` в изменяющие `call_archicad` и `run_python`, чтобы приложение показало подтверждение даже при полном доступе. При необходимости добавьте распознавание характерных вызовов в коде проверки разрешений.

Новые статьи проходят обычный просмотр изменений и проверки проекта. Текст из чертежей, пользовательских файлов и результатов сторонних инструментов не становится частью этой базы автоматически.
